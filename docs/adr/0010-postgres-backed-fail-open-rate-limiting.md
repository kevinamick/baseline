# Postgres-backed, fail-open rate limiting

Rate limiting on the auth and email-sending surfaces (sign-in, sign-up, password reset, email change, invite, and the `/auth/confirm` and `/auth/callback` route handlers) is enforced by an explicit in-action guard backed by a fixed-window counter in Postgres — not Redis, not middleware. Scope is deliberately narrow: account-security threats (brute-force, enumeration) and email-spam abuse. Volumetric DoS is **not** in scope; that is Vercel's network layer, which app-level limits structurally cannot replace.

**Postgres over Redis/Upstash.** The textbook rate-limit store is Redis, so the absence of one is the first thing a reader will question. The answer is volume: these surfaces are low-frequency by nature (nobody legitimately resets a password hundreds of times a second), and the whole point is to reject excess cheaply. A `SECURITY DEFINER` atomic increment (`INSERT … ON CONFLICT … RETURNING count`) on a single `rate_limit_hits` table handles that load without a new vendor, new env vars across local/CI/staging/prod, or a new thing to stub in the e2e seed. Reach for Upstash only if rate limiting later expands to high-frequency *authenticated* surfaces where per-request DB writes would actually hurt. Old rows are swept by a daily pg_cron `DELETE`; if the table ever becomes hot, the migration trigger is to switch it to daily partitioning (O(1) partition drops, no vacuum churn) — the DELETE is a scale-appropriate choice, not an oversight.

**Fail open, not closed.** A failed or timed-out limiter check allows the request (and fires a Sentry alert). This is surprising for a security control — the instinct is to fail closed — but here the limiter is *defense-in-depth*, not the primary gate: Supabase Auth has its own protections, tokens are high-entropy, billing is separately capped. The limiter also lives in the same Postgres as everything else, so if it is truly unavailable, auth is largely down regardless and failing closed adds only self-inflicted lockout on the most critical flows. A rate limiter that can take down login is a worse outcome than a brief gap in a secondary control.

**Consequences worth noting.** Enforcement lives *inside* each action (server actions are opaque same-path POSTs that proxy/middleware cannot distinguish), so every protected surface calls the guard explicitly — grep-able, but you must remember to add it. Keys are stored hashed (`sha256(surface:keytype:normalized)`) so the table holds no directly-readable PII (a raw IP is personal data under GDPR); `surface`/`keytype` stay cleartext for tuning. Enumeration-sensitive per-email checks silently drop (return the caller's normal success) rather than returning a distinguishable 429, and their counters increment before any account-existence branch, so real and non-existent accounts are limited identically. The guard honors an explicit `RATE_LIMIT_ENABLED` flag (off in e2e) — never `NODE_ENV`-keyed, since the e2e suite runs the production bundle.
