# next-intl, funnel-first localization

Localization is introduced with [next-intl](https://next-intl.dev) (`localePrefix: 'as-needed'`), driven by the goal of selling to non-English-speaking clients — Spanish (`es`) is the first locale, English (`en`) the source. The **entire app is moved under an `app/[locale]/` segment**, but only the prospect funnel — landing (`/`), `/pricing`, `/privacy`, `/sign-in`, `/sign-up` — is actually translated in v1. Locale lives in the URL (English unprefixed at `/pricing`, Spanish at `/es/pricing`); user-authored and model-generated content is never localized.

**Why the whole app is under `[locale]` when only five pages are translated.** This is the first thing a reader will question — it looks like a restructure out of proportion to the work. The driver is a planned fast-follow that localizes the private/authenticated routes. The App Router's root layout owns `<html lang=…>` and sits *above* any `[locale]` segment, so making `lang` locale-aware for a *subset* of routes forces an awkward choice: either a per-page `lang`-setting script hack (funnel under `[locale]`, app left flat), or two route groups with duplicated root chrome. Both are throwaway work once the app itself gets translated. Wrapping everything now pays the restructure cost once. The visible consequence in the interim: authenticated routes are reachable under a locale prefix (e.g. `/es/dashboard`) but render English until the fast-follow lands — an accepted, temporary gap, not a bug.

**next-intl over the native `getDictionary` pattern.** The Next 16 docs describe a dependency-free pattern (`server-only` dictionary loader + JSON), and for an all-Server-Component funnel that would have been proportional to v1. We took the library anyway: it is the de facto App Router standard with first-class RSC support, it provides `localePrefix: 'as-needed'` (exactly our unprefixed-English / prefixed-Spanish routing) out of the box, and — decisively — the fast-follow into the interactive, client-component-heavy authenticated app is where ICU pluralization, client-side translation, and `Intl` formatting earn their keep. Adopting it now avoids a hand-rolled-to-library migration later. The cost is one dependency to track against Next 16 and reconciling next-intl's routing with our existing single `proxy.ts`.

**Auto-detect and redirect, not stable URLs.** A cold visitor whose `Accept-Language` is Spanish is redirected from `/` to `/es`; the choice is then remembered in the `NEXT_LOCALE` cookie. Precedence is URL → cookie → `Accept-Language` → `en`. The simpler alternative — stable URLs reachable only via an explicit `/es` link — was rejected because the driver is *reaching* Spanish speakers, including organic traffic landing cold on the homepage; auto-landing them in Spanish is the higher-conversion behavior. The cost is redirect-on-marketing-pages, which is made SEO-safe with `hreflang` alternates and self-referencing canonical tags rather than left implicit.

**No in-app language picker (v1).** Locale follows the browser: detection sets it and the `NEXT_LOCALE` cookie makes it sticky. There is deliberately no visible switcher — a manual override is reachable only by visiting a prefixed URL directly (after which the cookie persists the choice). A picker was dropped as unnecessary chrome for an auto-detected, two-locale funnel; it can be reintroduced cheaply (it's a thin client island over next-intl's router) if a locale-mismatch need surfaces.

**Composition inside the existing `proxy.ts`.** Next allows exactly one `proxy.ts`, and it already mints the per-request CSP nonce, refreshes the Supabase session (rotating cookies), and redirects unauthenticated requests off protected routes. next-intl's routing is composed *into* it rather than replacing it: locale routing runs first (a detection redirect short-circuits, otherwise a rewrite to the internal `[locale]` path), the Supabase session refresh merges its rotated cookies onto that response, and the auth gate strips the locale prefix before testing `isPublicRoute` so it redirects to the locale-aware `/sign-in` (e.g. `/es/sign-in`). The `PUBLIC_ROUTES` exact-path regexes are locale-prefix-aware for the same reason.

**Catalog discipline and consequences.** `en.json` is the single source of truth; `es.json` is produced by machine-translation draft plus a native-speaker review pass (these are sales pages — clumsy MT Spanish repels the buyers it targets). Missing `es` keys **fall back to English at runtime** (never a 500 or blank) rather than failing the build. Two safety nets keep the catalogs honest: next-intl's typed keys make referencing an unregistered *source* key a compile error, and a CI `i18n:check` diffs `es.json` against `en.json` and reports missing/empty/orphaned keys; an `i18n:fill` script MT-drafts only the missing keys so reviewed translations are never clobbered. The discipline (keys instead of literal strings in JSX) applies **only to localized surfaces** — the funnel in v1 — so unrelated authenticated-app strings need not be refactored until their fast-follow. Domain nouns are translated through a single reused catalog key each, which keeps the Spanish rendering canonical without a second glossary; "Baseline" and the plan tier names (Free/Builder/Scale/Enterprise) stay English as proper nouns.

**Amendment (#363).** The catalog has since expanded into authenticated-app surfaces (starting with Settings → Connections). A third locale (`fr`) was added alongside `es`. A third safety net was introduced: per-feature Vitest structural parity tests (`connections-i18n.test.ts`) assert that every leaf key `en` defines for a catalog subtree is present in every other locale, failing the test suite rather than silently falling back at runtime. The prior statement that the discipline "applies only to localized surfaces — the funnel in v1" no longer holds; any authenticated-app component that ships catalog-backed copy should follow the same pattern. See `AGENTS.md` — "i18n message catalogs" for the current convention.
