# Accept the residual <24h password-change reauthentication gap

The in-app password change (#74) is gated behind an email reauthentication nonce: `changePassword` always drives `supabase.auth.reauthenticate()` (a one-time code to the account's current address) and then `updateUser({ password, nonce })`. That closes the "unattended logged-in browser" vector — anyone using the form needs a code from the owner's inbox. But GoTrue only *enforces* that nonce for sessions **older than 24h**. On a session created within the last 24h, `secure_password_change` skips the check: a `PUT /auth/v1/user` with a bogus nonce — or none at all — still changes the password. This is reproducible (a no-nonce `updateUser({ password })` on a fresh session returns `200` and changes it). #81 tracks the gap; this ADR records the decision to **accept** the residual risk rather than build new machinery to close it.

**The threat, scoped honestly.** What #74 already covers stays covered: the unattended-browser walk-up (the form always demands the emailed code) and any session older than 24h (GoTrue enforces a valid nonce even against direct API calls). What remains is narrow: an access token *hijacked within 24h of sign-in* can call GoTrue's `PUT /user` directly — bypassing both our UI and the nonce — to change the password. That is a provider ceiling: there is no GoTrue config to remove the 24h recency window, and the recovery-link flow has the same shape (any holder of a live bearer token can hit the endpoint). The precondition is itself a serious compromise (token theft), at which point the attacker already has the victim's full session regardless of the password.

**Why not the GoTrue notification email.** The obvious "detect, don't block" mitigation is `[auth.email.notification.password_changed]` — a notification GoTrue would send on *any* password change, including the direct-API path, alerting the owner with a one-click reset. The config key exists and our CLI accepts it, but **our GoTrue version does not actually send it**: enabling it and driving a real no-nonce password change against the local stack produced no Mailpit message, while a password-recovery email in the same run delivered normally (so SMTP→Mailpit routing was working — the notification simply never fired). Per our practice of verifying email/config changes against Mailpit rather than trusting config (it is exactly this kind of silent no-op that motivates that rule), an un-deliverable, un-testable notification is not shippable. Revisit if a GoTrue upgrade makes the notification fire and it can be Mailpit-verified.

**Why not an app-layer alert.** Sending the notification from our own server actions (`changePassword`, `resetPassword`) is trivial but misses the point: those actions only run on the UI and recovery paths, which are *already* gated. The one path that needs detecting — a direct `PUT /user` — never touches our code, so an action-sent email would not fire for the very attack it is meant to surface.

**Why not the heavier alternatives, yet.** Two real options remain on the table and are deferred, not dismissed:
- A **database-trigger detector** — an `AFTER UPDATE OF encrypted_password ON auth.users` trigger that `pg_net`-POSTs to an authenticated app route which sends the notification — *is* path-independent and would fire on the direct-API change. It is a genuine feature (trigger + `pg_net` + an HMAC-authenticated webhook route + Mailpit tests), and the security surface it adds (a callable internal endpoint) is non-trivial. The residual it closes does not justify that build today.
- **Shortening the access-token lifetime** shrinks the unprotected window but trades real UX (more frequent re-auth) for a partial mitigation, and is a product call, not a security necessity.

**Decision and compensating controls.** Accept the residual. It sits behind a provider ceiling, the precondition (a stolen in-window token) is already a broader compromise, tokens are high-entropy, and the surrounding controls — the #74 nonce gate on the UI path, ADR-0010 rate limiting on the auth surfaces, and Supabase's own protections — bound the realistic exposure. Revisit the trigger-based detector if and when we build a general `auth.users` security-event stream (password change, email change, new-device sign-in) worth the shared plumbing, or adopt the GoTrue notification once a version delivers it. #81 is closed as accepted, with this ADR and the note in `changePassword` as the durable record.
